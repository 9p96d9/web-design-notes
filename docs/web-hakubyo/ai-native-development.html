AIと共同開発する技術
SPEC駆動・自走エージェントの設計思想

AI・開発手法 2026/05/20

「AIに指示してたはずが、AIが実行していた」

最初はこうだった。

人間 → 「CloudShellでこれ実行して」 AI → コードを出力 人間 → コピペして実行 AI → 「結果を貼ってください」 人間 → コピペ

AIは アドバイザー でしかなかった。人間がすべて実行していた。

ある時、AWS CLIをローカルに入れた。gh CLIを認証した。SPEC.mdを整理した。
するとフローが変わった。

人間 → 「phase_plan.md で設計を確認して実装して」 AI → AWS状態を確認 → コード変更 → デプロイ → テスト 人間 → 結果を確認して「OK」

AIが 実行者 になった。人間は 承認者 になった。

この変化に必要だったのは、最新の道具ではなく、設計の思想 だった。

① SPEC.md を「真実の源」にする意味

開発現場でよく起きる問題がある。仕様書が腐る、というやつだ。

よくある失敗パターン：
仕様書を書く → 実装する → 現実が仕様とズレる → 誰も仕様書を更新しない → 仕様書が「過去の遺物」になる → コードを読むしかなくなる

人間なら「まぁ察する」ができる。でもAIは 仕様を真に受ける。

古い仕様書をAIに渡すと、こうなる。

  • 存在しないAPIを呼ぶコードを書く
  • 削除済みのテーブルを前提にする
  • 古い環境変数名を使う
  • 変更されたディレクトリ構造でパスを組む

つまり AIが壊れる。コードが正確なのに、前提が間違っているせいで動かない。

解決策はシンプルだ。

SPEC = 理想 ではなく、SPEC = 現実 にする
実装が終わってから SPEC.md を更新する。仕様書が「今動いているものの記録」になる。

流れはこうなる。

設計を合意する ↓ 実装する ↓ 動作を確認する ↓ SPEC.md を更新する（←ここで初めて書く） ↓ コミット

「実装前に書くと実装とズレる。実装後に書くと確実に一致する。」

これが SPEC駆動の核心だ。AIに渡す地図を、常に最新に保つ。

② 設計合意ファイルの役割

SPEC.md が「現在の話」なら、設計合意ファイルは 「未来の話」 だ。

ファイル役割タイミング
SPEC.md現在の実装の現実実装後に更新
phase_plan.mdこれから何をどこまでやるか実装前に合意

phase_plan.md には「なぜやるか・何を変えるか・どこまでやるか」を書く。

## Phase 21: needs_api バッジ削除 目的: UIから実装待ちバッジを消す 変更: frontend/components/Badge.tsx を削除 やらないこと: バックエンドの変更・DB更新

この「やらないこと」が特に重要だ。

AIは善意で余計なことをする。指示していないのに「ついでにリファクタリング」「関連ファイルも修正」をやりがちだ。
設計ファイルで 境界を先に固定 することで、スコープの爆発を防げる。

設計合意のある開発： AIが「どこまでやるか」を理解した状態で動く。余計な変更が入らない。

③ AWS CLI 導入で AI が「実行者」になる

ここが、フローが変わった最大のポイントだ。

AWS CLIをローカルに入れる前と後を比べると、AIの立場が根本的に変わる。

CLI なしCLI あり
AIの立場アドバイザー実行者
人間の立場実行者承認者
EC2の状態確認人間がコンソールで確認・コピペAIが直接確認
デプロイ人間がコマンドをコピペ実行AIが直接実行

CLIの設定は一度だけだ。

# AWS CLI のセットアップ aws configure # Access Key ID、Secret Key、リージョンを入力 # 接続確認 aws sts get-caller-identity

これ以降、AIはコンソール→CloudShell→コピペのループなしに、直接インフラを操作できる。

同じことが GitHub CLI でも起きる。gh auth login で認証すれば、AIが GitHub Secrets の更新・PR操作・Actions確認を自走できる。

CLI = AIが動ける範囲を広げるレール
人間が一度設定するだけで、AIが継続的に使える。

④ 破壊的操作だけ承認制にする理由

「AIに全部任せる」は危ない。でも「全部確認する」は遅い。

答えは操作の種類で分けることだ。

操作の種類例扱い
読み取り・観測describe-instances, docker ps, logs確認自動実行
コード変更・デプロイファイル編集, git push, docker restart自動実行
破壊的・不可逆EC2停止, RDS削除, Secrets削除確認を取る

破壊的操作の特徴は やり直せない ことだ。

  • stop-instances → EC2が停止（本番サービスが落ちる）
  • rds delete → データが消える
  • terminate → インスタンスが消える
観測は自動化、破壊は承認制
リスクの低い操作を自動化して速度を上げ、リスクの高い操作だけ人間が判断する。

コストの低い確認をケチると、コストの高い事故が起きる。逆に確認しすぎると、自走の意味がない。この設計がちょうどいいバランスだ。

⑤ 小刻みテストで自走する開発

AI開発で一番危険なパターンがある。

やりがちな失敗：
大量変更 → 最後にまとめてテスト → 壊れた場所が分からない

AIは1回の出力で10ファイル・数百行を同時に変更できる。
それを全部まとめてテストすると、どこで壊れたか追跡できなくなる。

正しいフローはこうだ。

1つ変更する ↓ 即テストする ↓ 通ったら次へ

人間の開発でも同じ原則だが、AIの場合はより重要だ。AIは「勢いで壊す」からだ。

フェーズごとにテスト方法をあらかじめ決めておくと、AIが自走できる。

変更の種類テスト方法
Pythonコード変更構文チェック → ローカルで起動確認
API変更curl で直接叩く
インフラ変更AWS CLI で状態確認 → SSH で docker 確認
デプロイ後health check + docker logs

「次のテストは何か」が決まっていれば、AIは確認を取らずに先へ進める。

⑥ curl health check と Docker logs が重要な理由

テストの最終確認として特に有効な2つがある。

curl によるヘルスチェック

curl https://example.com/health

これは単純に見えて、実は多くのレイヤーを一気に貫通している。

DNS → HTTPS → nginx → アプリサーバー → ルーティング → コンテナ → プロセス

「ユーザーから見えている現実」を確認できる唯一の方法だ。
ログを見るだけでは「内部的には動いているが外から死んでいる」状態を見逃す。

Docker logs の確認

docker logs gto-app --tail 50

コンテナが起動していても、内部でクラッシュして再起動ループしている場合がある。
AIは「起動成功」を過信しがちだ。ログを見ると実態が分かる。

  • マイグレーション失敗
  • 環境変数の不足
  • importエラー
  • ポート競合

これらは起動直後のログにしか出ない。

health check + docker logs = 「外から」と「内から」の両面確認
どちらか一方では不十分。セットで使う。

⑦ AI-native 開発とは何か

ここまでの話をまとめると、共通のテーマが見えてくる。

AI が継続的に正しい世界認識を持てる環境を作ること

従来の開発は「人間が主体、AIが補助」だった。
AI-native 開発は「AIが作業主体、人間が設計と承認」に近づく。

そのために必要な設計の要素をまとめると：

設計目的
SPEC.md = 現実AIに正しい地図を渡す
設計合意ファイルAIのスコープを固定する
CLI 化AIが実行できる範囲を広げる
破壊だけ承認制速度と安全のバランスを取る
小刻みテスト壊れた場所を特定しやすくする
health checkユーザー視点の現実を確認する

これらはどれも「AIのためのレール整備」だ。

レールが整っていれば、AIは自走できる。
レールが崩れていると、どんなに賢いAIでも道に迷う。

「どんなツールを使うか」より「どんな環境を作るか」が、AI共同開発の本質だ。
