拡張機能を消してもログイン状態が残る理由
Chrome の OAuth 階層構造

Webリテラシー 2026/05/20

「消したのに残ってる」の謎

Chrome拡張機能を削除して再インストールしたのに、Googleログイン画面が出ない。
メール入力もパスワード入力もスキップされて「アカウントを選択してください」だけ出る。

ありがちな誤解：
拡張機能を削除した → データが全部消えた → ログイン状態もリセットされたはず

実はこれ、バグでも不具合でもない。
Chromeが 優秀すぎる副作用 として意図的にやっていることだ。

理解するには、Googleログインが実は 3つの別々の層 で管理されていることを知る必要がある。

① Googleログインの3層構造

拡張機能を「削除する」と消えるのは、3層のうち1層だけだ。

第1層：拡張機能自身のストレージ

これは拡張機能が自分で保存するデータだ。

  • localStorage
  • chrome.storage.local
  • IndexedDB

設定・APIキー・UI状態などがここに入る。拡張機能を削除すると ここは消える。

第2層：Chrome本体のOAuthセッション

Googleログインを使う拡張機能の多くは、内部でこの関数を呼んでいる。

chrome.identity.getAuthToken({ interactive: true }, function(token) { // Googleのアクセストークンが返ってくる });

これを呼ぶと、Chrome本体が「この拡張機能はこのGoogleアカウントへのアクセス許可済み」という情報を記憶する。
拡張機能を削除しても、Chrome本体の記憶は消えない。

第3層：Google側のOAuth許可情報

さらに奥には、Googleアカウント側の記録がある。
myaccount.google.com/permissions を開くと確認できる場所だ。

「このアプリに、いつ、何の権限を許可したか」がGoogleサーバーに残っている。
これも拡張機能の削除とは完全に独立している。

層何が入っているか拡張削除で消えるか
拡張機能ストレージ設定・APIキー・UI状態✅ 消える
Chrome OAuthセッション「このアプリ許可済み」の記憶❌ 残る
Google側の許可情報アプリへのアクセス権記録❌ 残る

② OAuthは「ログイン」ではなく「許可」

多くの人が「Googleログイン = Googleにログインすること」と思っている。

でも内部で起きているのはそれじゃない。

OAuthの本質：「このアプリにGoogleアカウント情報を渡していいか」という許可システム
ログインではなく、アクセス権の委譲。

だからGoogle側には「どのアプリに・どの権限を・いつ許可したか」が記録として残る。
「ログアウト」や「拡張機能削除」はこの記録に触れない。

ユーザーが「Googleでログイン」をクリック ↓ Googleが「このアプリにプロフィール情報を渡していいですか？」と確認 ↓ ユーザーが「許可」 ↓ アプリがアクセストークンを受け取る ↓ Google側に「許可した」記録が残る

この許可を取り消すには、Googleアカウントの設定から明示的に削除する必要がある。

③「アカウント選択だけ出る」の正体

拡張機能を再インストールしてもメール入力が出ず「アカウントを選択してください」になるのは、Chromeがこのデータを持っているからだ。

Chromeが記憶していること
このPCで使ったGoogleアカウントの一覧
各アカウントのログインセッション
このアプリへの許可が存在すること

つまりGoogleから見ると「誰か」はすでに知っている。だから確認するのは「どのアカウントで使うか」だけになる。

普通の状態： メール入力 → パスワード → OAuth許可 → 完了 再インストール後： アカウント選択 → 完了（残りはスキップ）

Googleの設計思想として「毎回ログイン入力させるのはUXとして最悪」があるため、
可能な限りステップを省略する方向に作られている。

④ 本当の初回状態を作る方法

「完全に初回のユーザー体験」を再現したい場合（UIテスト・録画など）、方法は3つある。

方法A：ゲストモード（最も確実）

これが最強。
Chrome右上のアイコン → 「ゲストとして閲覧」

ゲストモードは「人格そのものを新規生成」する感覚だ。

  • OAuthキャッシュなし
  • Cookieなし
  • Chrome Profileなし
  • アカウント選択履歴なし

これで100%の初回状態になる。

方法B：新規Chromeプロファイル

右上アイコン → プロファイル追加で新しい「人格」を作る。ほぼ初回の状態になる。
ゲストモードと違いデータが残るので、開発用テストアカウントとして使い続けられる。

方法C：シークレットモード

Cookieは消えるが、Chrome拡張のidentity APIの挙動が通常モードと変わる場合がある。
拡張機能の動作確認には向かないことが多い。

方法初回再現度向いている用途
ゲストモード◎ 完全録画・UXテスト
新規プロファイル○ ほぼ完全開発用テストアカウント
シークレットモード△ 部分的Cookieのみリセットしたい場合

⑤ ブラウザは半分OSになっている

昔のブラウザは「HTMLを表示するだけのソフト」だった。
今のChromeが管理しているものを並べると、その変化がよくわかる。

機能具体的な内容
認証基盤Googleアカウント・OAuthトークン管理
ストレージCookie・localStorage・IndexedDB・キャッシュ
アプリ実行環境Chrome拡張機能・PWA
アカウント同期パスワード・履歴・タブをデバイス間で共有
通知Push通知の受信・管理
決済Google Payとの連携

Chrome Profileはこれらをまるごとひとまとめにした「人格」だ。
プロファイルを切り替えると、認証・拡張・履歴・設定が全部別になる。

「拡張機能のデータ」と「ブラウザが持つ認証状態」は別の引き出しに入っている
今回の現象は、引き出しを1つしか空けていなかったことで起きた。

SaaSやWebアプリを開発するときも同じ視点が重要だ。
自分の開発環境はすでにログイン済み・許可済み・Cookie保持済みになっている。
「初回ユーザーの体験」を確認するには、ゲストモードや別プロファイルで意図的にリセットする必要がある。
