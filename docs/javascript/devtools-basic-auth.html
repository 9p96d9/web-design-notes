401エラーを解剖する
DevToolsでBasic認証を特定してスクレイプする

JavaScript・DevTools 2026/05/28

「401が返ってくる」だけでは何もわからない

Pythonスクリプトでサイトの画像をまとめてダウンロードしようとしたとき、全件 HTTP 401 Unauthorized で弾かれた。

401は「認証が必要」という意味だが、認証方式は1種類ではない。方式を特定しないと対処できない。

認証方式仕組みよくある用途
Cookie認証ログイン後にCookieを発行し、以降のリクエストに自動添付一般的なWebサービスのログイン
JWT / BearerAuthorization: Bearer <token> ヘッダーで送るSPA・API認証
Basic認証ID:パスワードをBase64エンコードして Authorization ヘッダーに入れる静的サイトのアクセス制限
OAuthアクセストークンを外部プロバイダ経由で取得するSNSログイン・APIアクセス

まず「このサイトはどの方式を使っているのか」を特定する必要がある。最初は Cookie 認証だと思い込んで、ハマった。

document.cookie の限界 — HttpOnly Cookie は見えない

最初に試みたのは Chrome DevTools の Console から document.cookie を取得することだった。

// Console で実行 document.cookie // → "session_id=abc123; pref=dark"

取得できたCookieをPythonスクリプトの headers に追加して再試行したが、まだ401のままだった。

なぜ Cookie を渡しても401のままなのか？
document.cookie で取得できるのは、JavaScriptからアクセス可能なCookieだけだ。
HttpOnly フラグが付いたCookieは、XSS攻撃への対策としてJSから読めないように設計されている。
つまり認証に使われているCookieが HttpOnly であれば、Console からは取得できない。

「HttpOnly Cookieはどこで確認できるのか？」と思い、Application タブを開いた。

DevTools → Application タブ → Storage → Cookies → ドメインを選択 → 全Cookieの一覧と HttpOnly フラグが確認できる

確認すると、そのドメインのCookieは3件だった。document.cookie で取得できたのも同じ3件で、HttpOnly のものはなかった。

ここで気づいたこと：
Cookie の問題ではなく、そもそも認証方式がCookieではない可能性がある。
原因を決めつけず、まず「サーバーが何を要求しているか」を確認すべきだった。

WWW-Authenticate ヘッダーで認証方式を特定する

401レスポンスには、サーバーが要求する認証方式を示す WWW-Authenticate ヘッダーが含まれることがある。これを見れば方式が一発でわかる。

確認方法はいくつかある。最も簡単なのは curl.exe -I でヘッダーだけを取得することだ。

# Windows PowerShell / ターミナルで実行 curl.exe -I https://example.com/works/web/osanpo/img/zukan01.jpg
# レスポンス（抜粋） HTTP/1.1 401 Unauthorized WWW-Authenticate: Basic realm="Restricted Area" Content-Type: text/html

WWW-Authenticate: Basic realm="..." が返ってきた。Basic認証だった。

同じ情報はDevToolsのNetworkタブからも確認できる。

DevTools → Network タブ → 401になったリクエストをクリック → Headers → Response Headers → WWW-Authenticate を確認
WWW-Authenticate の値認証方式
Basic realm="..."Basic認証（ID・パスワード）
BearerOAuth 2.0 / JWT
Digest realm="..."Digest認証
（ヘッダーなし）独自実装・Cookie認証の可能性

Disable cache でリクエストヘッダーを「本物」にする

認証方式がBasicだとわかった。次はブラウザが実際にどんな Authorization ヘッダーを送っているかを確認したかった。

しかし、NetworkタブでリクエストのHeaders を見ると「Provisional headers are shown」と表示されていて、Authorization ヘッダーが見当たらない。

「Provisional headers are shown」とは何か？
キャッシュからレスポンスが返ったとき、ブラウザは実際にはリクエストを送っていない。
そのためDevToolsには「送る予定だったヘッダー（暫定ヘッダー）」しか表示されず、
実際に送信された認証ヘッダーは見えない。

これを解決するには、キャッシュを無効にしてから再リクエストさせる必要がある。

DevTools → Network タブ → 「Disable cache」にチェックを入れる → ページをリロード（またはリソースを再取得） → 今度は実際のリクエストが発生する

「Disable cache」にチェックを入れてリロードすると、zukan01.jpg のリクエストヘッダーに以下が現れた。

Request Headers: Authorization: Basic b3lhc3VtaTE5OTc6cGFzc3dvcmQxMjM=
これが「本物」の Authorization ヘッダーだ。
Basic の後の文字列は username:password をBase64エンコードしたもの。
このまま Python スクリプトの headers にコピーして使える。
Base64のデコード確認方法（確認したいとき）：
atob('b3lhc3VtaTE5OTc6cGFzc3dvcmQxMjM=') を Console で実行すると元の文字列が見える。
ただし実運用では値をそのままコピーするだけでよい。

Authorization ヘッダーをスクリプトに追加して完了

取得した Authorization ヘッダーの値を Python スクリプトに追加する。

import urllib.request # DevTools から取得した Authorization ヘッダーをそのままコピー headers = { 'Authorization': 'Basic b3lhc3VtaTE5OTc6cGFzc3dvcmQxMjM=', 'User-Agent': 'Mozilla/5.0', } url = 'https://example.com/works/web/osanpo/img/zukan01.jpg' req = urllib.request.Request(url, headers=headers) with urllib.request.urlopen(req) as res: data = res.read() with open('zukan01.jpg', 'wb') as f: f.write(data) print('ダウンロード完了')

複数ファイルをまとめてダウンロードするときは、URLリストをループさせるだけでよい。

image_urls = [ 'https://example.com/works/web/osanpo/img/zukan01.jpg', 'https://example.com/works/web/osanpo/img/zukan02.jpg', # ... ] for url in image_urls: filename = url.split('/')[-1] req = urllib.request.Request(url, headers=headers) with urllib.request.urlopen(req) as res: with open(filename, 'wb') as f: f.write(res.read()) print(f'完了: {filename}')

実行すると全件ダウンロードが成功した。

まとめ — 401のデバッグ手順

今回の調査で整理できた、401に詰まったときの確認フローをまとめる。

① curl -I または Network タブで WWW-Authenticate ヘッダーを確認 → 認証方式を特定する ② Cookie認証が疑われる場合 → Application タブ → Cookies で HttpOnly フラグを確認 → document.cookie では HttpOnly は取れない点に注意 ③ Basic認証の場合 → Disable cache にチェック → リロード → Request Headers の Authorization: Basic ... を取得 ④ スクリプトの headers に Authorization を追加して再試行
確認ポイント場所わかること
WWW-Authenticatecurl -I / Network > Response Headersサーバーが要求する認証方式
AuthorizationNetwork > Request Headers（Disable cache後）ブラウザが実際に送っている認証情報
HttpOnly CookieApplication > CookiesJSから見えないCookieの有無
Provisional headersNetwork > Request Headersキャッシュ利用時は「暫定」で本物ではない

401は「認証失敗」という結果を表すだけで、原因は様々ある。まずサーバーのレスポンスヘッダーを読むという習慣を持つことで、無駄なトライ&エラーを減らせる。
